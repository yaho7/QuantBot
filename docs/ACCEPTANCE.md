# QuantBot 3.0 acceptance matrix

The previous product baseline is commit `9f96182`. Prior-version tests informed the scenario list; the evidence below is from 3.0.

| Area | Verification |
| --- | --- |
| Initialization, authentication and proxy | Go tests cover first-run setup, password change, CSRF, rate limiting, session revocation and HTTPS headers from explicitly trusted peers. Browser setup and real Compose login passed. |
| Strategy registration and Agent lifecycle | Go HTTP tests cover token issuance, archive, scope changes, boot fencing, executor designation, offline detection and immediate revocation, including an active long poll. All four paper examples renewed the same boot against an eight-second Session TTL. |
| Declared capabilities and layouts | Go tests cover declaration replay, compatible updates, removed capabilities, invalid types, staleness, resource revision conflicts, patch/snapshot retry and explicit associations. Browser and unit checks cover suggested widgets, saved size and visibility, and preserving a saved layout after registry or theme changes. |
| Reporting and history | Schema tests cover 14 standard report kinds and exact decimal values. Tests verify mixed-database replay after SQLite FULL and write lock contention, fill deduplication, durable acknowledgement, queue drain, point budgets, late candle ordering and exact volume. |
| Trading control and recovery | Browser runs confirmation, one-time grant, receipt and separately reported actual state. Go tests race 16 claim requests, simulate a lost response and restart, verify no second permit, and reconcile uncertain outcomes. Unavailable risk-locked controls and offline targets are rejected. The server only routes declared operations; strategy code decides how to pause and retains its own risk and exit checks. |
| Live workbench and administration | Authenticated SSE tests verify commit-aware invalidation. Playwright exercises live values, charts, association lookup, layout changes, audit, notification setup, storage and effective settings. Screenshots cover five widths in light and dark. |
| Theme packages | Go tests cover archive validation, install, update, configure, rollback, deletion and asset isolation. Playwright uploads a frontend theme, checks it cannot access the auth API, exercises the trusted control dialog and verifies Classic recovery when the theme fails to initialize. |
| AI integration and Sandbox | Go tests exercise all ten Agent operations in the isolated runtime and cover expiry, rotation, revocation, global limits and rejection of production credentials on the trial. Browser verifies temporary key issuance, simulated command creation, request history and revocation. |
| Bot notifications | Browser configures an encrypted channel and checks credentials stay out of read responses. Simulated Telegram, Feishu/Lark, WeCom and DingTalk transports verify request format, signatures, acknowledgement and retry. Delivery is outbound; the application has no Telegram command receiver. |
| Deployment and recovery | Native and Compose checks cover clean startup, initialization, health under the unprivileged runtime UID, diagnostics, backup, new-volume restore and login after restart. Restore tests verify token revocation and quarantined interrupted commands. Docker builds and smoke checks cover Linux amd64 and arm64. |
| Load testing | [Benchmarks](BENCHMARK.md) cover idle, 10/100/1000 Agents, high-rate telemetry, mixed control, 500 SSE subscribers, history, SQLite and theme switching. Persisted counts match expected samples. |

The release workflow runs Go race tests and vet, the frontend build and unit tests, Playwright, and clean Compose smoke checks on native runners for both architectures. Tag publication depends on those checks. Live bot credentials, broker operations, and a hosted VPS were not used in verification. Benchmarks use local storage, including a Linux container capped at 2 CPUs and 2 GiB. The simulated strategies make no broker calls.
